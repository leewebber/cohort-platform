## 2. Exact supported grammar and editing operations

The wrapper is `schema_version: 1`, with fixed synthetic `programme.import_key`, `programme.code`, title/description/objective, `duration_weeks: 1`, declared `sessions_per_week: 1`, one week numbered 1, one non-rest day numbered 1, and one session. Wrapper identity and schedule are read-only; they transport a session body, not a second catalogue schedule. All accepted wrapper fields are emitted completely. Omitted optional values remain absent; parser-defined trimming/empty normalization is explicit, not formatting preservation.

One session has `session_type: strength`; exactly one `block_type: strength`, `order: 1`, and no timer, execution groups or legacy step input. It compiles to `ProtocolDraft.sessionFormat = structured_strength`, one `SessionBlock` with `WorkoutFormat.none`, and one typed `SessionBlockExerciseLink` per exercise.

| Field | D2 author operation / valid input |
|---|---|
| Session `title`, `coach_notes`, `estimated_duration_minutes` | Edit required nonblank title, optional string notes and optional positive integer minutes. Title is a label, not identity. No duration calculation. |
| Block `title`, `coach_notes` | Edit required nonblank title and optional notes. Block type/order stay fixed. |
| Exercise `transitional_exercise_id` | Explicit selection from two fixed synthetic fixture identities only. Required; no free-text identity creation. |
| Exercise `exercise_name` | Optional display-only label. It cannot change the resolved exercise ID or rescue a failed ID. |
| Exercise `order` | Explicit add/remove/move operations, with confirmation for removal/replacement. Dense 1..N order matching source list order. One or two rows, no duplicate resolved canonical exercise within the block. New rows start with incomplete dosage and cannot validate until the author enters it. |
| Prescription `sets` | Required positive integer. Uniform across all working sets. |
| Prescription `reps` | Required positive integer exact reps. Also accept the existing exact-map spelling `{type: exact, exact_reps: N}` at intake; normalize export to the scalar integer. No range/duration/distance/AMRAP/free-text reps. |
| Prescription `rest_seconds` | Optional positive integer seconds. Absence means unspecified. Reject zero/negative, fractions, ranges and unit strings; do not silently clear them. This deliberately narrower D2 boundary avoids legacy projection dropping an authored zero. |
| Prescription `tempo` | Optional opaque authored string, displayed explicitly. No interpretation, generated tempo or enforced invented syntax. |
| Prescription `notes` | Optional cue text; maps to typed `coachCue` / canonical `coach_cue`. Distinct from block/session notes. Reject row-level `exercise.notes` because the current private draft builder does not retain it on the link. |
| Prescription `load` | Exactly one of no load, `{unit: bodyweight}` without `value`, `{unit: kg, value: X}` with positive finite numeric kg, or `{unit: rpe, value: N}`. No conversion of pounds or other units. No load is unspecified, not assumed bodyweight. |
| Prescription `target_rpe` | Intake-only existing alias for RPE load, accepted only when `load` is absent. Canonical export uses `load.unit: rpe`. Any simultaneous `load` and `target_rpe` is an error, even if equal. |

**Proposed D2 RPE input bound:** integer 1..10. The existing strength mapper/model only enforce positivity; the 1..10 bound is an explicit stricter D2 intake rule to be approved with this allocation, not a claim about the shared compiler. Fixed kilograms may be fractional; NaN/infinity and nonnumeric input fail before mapping. No mode switch discards hidden values without an explicit author choice; discarded incompatible draft inputs are shown in the source diff.

The existing mapper has other capabilities (rep ranges, percent-1RM aliases, RIR, duration/distance/max effort, performance capture). They are **not** D2 capabilities. The application strength model additionally understands per-side, calories and distance fields that the Founder importer does not preserve. Do not infer importer support from that larger model. Unknown source keys at every level, unsupported modes, conflicting aliases, malformed numeric values, non-string labels, wrong wrapper identity, additional weeks/days/sessions/blocks and unsupported null/collection shapes are refused before the permissive parser can drop/coerce them. The intake must detect duplicate mapping keys and refuse multiple documents, merge keys, custom tags or unresolved alias constructs. Retain rejected original source bytes for correction; never replace them with a partial normalized document.

## 5. Immutable revision rules

- Use existing `(protocolId, sessionLineageId, revisionNumber)` and package `session_key` conventions. One fixed synthetic session lineage; positive integers, new number = max known/reserved + 1, never overwrite/reuse an existing or abandoned reservation during the preview.
- Reserve IDs using `SessionRevisionClone.revisionProtocolIdForNumber` from a fixed synthetic root, with deterministic source provenance. E.g. base protocol root `syn-d2-strength-r1-w1-d1-s1`, new revision ID `<root>-rev-2`, session key `SYN-D2-STRENGTH-R2`, unchanged lineage. No time/random ID in source export, body semantic comparison or local review artifacts.
- Founder YAML has no protocol/lineage/revision fields. Keep a read-only wrapper import key per revision (`syn-d2-strength-r1`, `syn-d2-strength-r2`, …) associated with the existing identity tuple in the local catalogue. Do not add identity fields to Founder YAML. The upstream importer's own ID formula would yield a different R2 protocol ID and would create/replace programme draft v1; **D2 does not claim its YAML can apply the local revision identity through that persistence path**. Exact mapping belongs to local provenance/package reference, not a new canonical body schema.
- Mutable working draft is separate from immutable retained snapshots. Creating an unselected draft does not change R1 or its programme references; freeze does not select it; explicit confirmed selection does. Further edits to a frozen snapshot require another local working revision.
- All snapshots keep `lifecycle_status: draft`, `published: false`. Production M9 distinguishes mutable drafts from immutable published/archived revisions and refuses its new-revision service for draft sources. D2's stricter read-only fixture snapshots are a local test boundary, not simulated publication. Do not call that service or alter its policy.
- Reopen under an already frozen identity with different compiled meaning or bindings is an immutable-revision conflict. Different formatting may be inspected, but cannot replace the retained snapshot's exact source bytes/digest. Unknown identities, duplicate tuple/ID/key, nonpositive revisions, catalogue mismatch or wrong source binding fail closed.
- Synthetic package stays an unpublished v1 candidate, never a real pinned/published version. New programme publication/version/default/pin behavior is excluded.
