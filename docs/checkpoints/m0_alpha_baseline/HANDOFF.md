## Workflow findings — progression, adaptation and recovery

**Progression has three different meanings.** Programme advancement after completion
is already owned by atomic completion plus the authored next slot. Previous-performance
recall and observational comparisons are separate: Active Session uses
PreviousStrengthPerformanceService (owned completed actuals), format comparators delegate
to current `performance/progression` logic, and Progress uses programme evidence plus
owned performance projections. Current vocabulary includes First performance, Improved,
Matched, Mixed, Below last performance, Not comparable and Insufficient evidence.
The old implementation-audit complaints about estimated-1RM verdicts are historical;
current StrengthResultComparison delegates to StrengthProgressionComparison.

There is no approval for automatic load/repetition/protocol progression from those
results. M5 progression/trends means useful honest observations, not automatic changes.
Correction replaces effective evidence and invalidates recall; later actual records
are required to prove real longitudinal usefulness. The independent Distance History
screen/C2/C3 profile pipeline is observational, not authority for B2 benchmark eligibility
or a universal finished dashboard. Do not treat missing contexts as comparative proof.

**Production adaptation trace:** Home → AthleteProgrammeTodaySection → ProgrammeAdaptFlow
→ reason questionnaire → ProgrammeAdaptationProposalService → PlanPackageSessionAdaptationAdapter
→ SessionAdaptationPipeline → review sheet → explicit Accept → revalidated proposal →
replace only current prepared execution package. Cancel/dismiss/no-safe paths preserve
it; revert reconstructs the original through prepare. Programme, later sessions, actuals
and schedule remain distinct. This is stronger than an isolated planner test, but it
also exposes the real default wiring gaps:

- Both proposal and acceptance default permission loaders return `[]`. Production Home
  does not inject them. Equipment substitution requires a matching authored permission;
  therefore normal production equipment requests refuse before the swap planner can help.
  Staging injected fixtures prove the engine, not normal production capability.
- Time planning exists when authored duration/minimum/priority/limits suffice. Content
  coverage and installed knowledge loading still need the real-session check. The default
  knowledge loader resolves a YAML directory; desktop local proof is not proof of packaged
  iOS asset availability. Do not claim a confirmed mobile failure without that check.
- Recovery input can produce conflict findings, but no dedicated recovery-plan branch
  was found. No time/equipment constraint leads to no-plan-required; actionable safe
  recovery suggestions remain an implementation gap.
- Engine-generated per-exercise equipment replacements are not an athlete-selected
  exercise-swap journey. No chooser in normal Home/Active Session was found.

Source links and exact hashes for these findings are in EVIDENCE.json. Relevant read
coverage includes `test/application/adaptation/`, the Home widget tests and the staging
Journey D injected loaders. They were inspected, not rerun as fresh proof.

**Execution/recovery trace:** canonical launcher compares provenance and calls the
atomic create/resume store; verified running mapping/targets accompany Active Session.
Draft-save coordinator + ProductionRestoreEnvelope retain progress; complete goes through
AthleteProgrammeCompletionService and server transaction rather than the legacy progression
coordinator. Training History detail correction delegates to the correction RPC. This
supports safe retry boundaries in code/local proof. It does not promise offline queued
completion or losslessness on an untested current release build. B3 phone proof did not
submit a genuinely changed correction, so it did not close audit-row creation on-device.
